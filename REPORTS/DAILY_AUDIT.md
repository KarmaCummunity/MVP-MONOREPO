**Scope:** 994 tracked files, with focused call-chain review of `apps/api`, `apps/mobile`, current SSOT requirements, and recent changes through `3d92f9d`. Automated checks included secret/auth/SQL/transport scans, source-size inventory, and `npm audit --workspaces --audit-level=moderate`.

## 🚨 Critical Vulnerabilities

* **[CRITICAL] Tracked deployment credentials are present in the repository.** `apps/api/railway_vars.txt:8-37` contains a database URL with password, a Google API key, and a JWT signing secret; `apps/api/railway.toml.dev:33-34` contains another JWT secret; `apps/api/src/main.ts:149-189` embeds recognizable database-password fragments; `apps/api/data-backups/20251224-162421/users.json` is also tracked and contains password-hash material. Repository history must be treated as compromised. - File: `apps/api/railway_vars.txt`, `apps/api/railway.toml.dev`, `apps/api/src/main.ts`, `apps/api/data-backups/20251224-162421/users.json` -> Action: Rotate every exposed credential immediately, revoke active JWT/refresh sessions, remove secret and backup material from Git history, replace password-fragment environment detection with non-secret environment identifiers, add ignore rules, and enable CI secret scanning.
* **[CRITICAL] `POST /api/users/resolve-id` mints access and refresh tokens from an unverified email, Firebase UID, or Google ID.** The route has no guard (`users.controller.ts:183-188`), performs identifier lookup (`user-auth.service.ts:270-342`), can link caller-supplied identifiers (`user-auth.service.ts:580-630`), and returns a token pair (`user-auth.service.ts:645-672`). Knowing a victim's email is sufficient for account takeover; supplying an attacker-controlled UID can also bind it to a profile whose UID is empty. The SRS currently documents token output without requiring identity proof, which conflicts with §3.2 authentication guarantees. - File: `apps/api/src/controllers/users.controller.ts`, `apps/api/src/services/user-auth.service.ts` -> Action: Require a verified Firebase/Google credential or password before lookup, linking, or token issuance; never mint tokens from email knowledge alone; rate-limit and audit the endpoint.
* **[CRITICAL] Any authenticated user can update any profile and assign privileged roles.** `PUT /api/users/:id` checks only for a valid JWT and does not bind `:id` to the JWT subject (`users.controller.ts:126-132`). `updateUser` accepts `roles` and `firebase_uid` (`user-profile.service.ts:254-361`), protecting only the configured root account. A normal user can promote themselves or another account to `admin`/`super_admin`. - File: `apps/api/src/controllers/users.controller.ts`, `apps/api/src/services/user-profile.service.ts` -> Action: Enforce self-or-admin ownership, remove identity/role/hierarchy fields from the self-service DTO, and expose role changes only through an admin-guarded use case using the authenticated actor.
* **[CRITICAL] Hierarchy authorization trusts client-supplied identities and fails open when one is omitted.** Promotion routes accept `requestingAdminId` from the body (`users.controller.ts:64-88`) and authorize that database user rather than the JWT subject (`user-hierarchy.service.ts:945-1050`). `set-manager` skips its admin check entirely when `requestingUserId` is absent (`user-hierarchy.service.ts:492-517`, `600-615`). Any JWT holder can impersonate a known admin UUID or rewrite reporting lines without supplying an actor. - File: `apps/api/src/controllers/users.controller.ts`, `apps/api/src/services/user-hierarchy.service.ts` -> Action: Derive the actor exclusively from `req.user`, apply `AdminAuthGuard`, reject actor IDs in request bodies, and add permission-matrix tests.
* **[CRITICAL] Multiple controllers expose PII and state-changing operations without authentication or ownership checks.** Confirmed surfaces include CRM CRUD (`crm.controller.ts:38+`), community-member contact CRUD (`community-members.controller.ts:48+`), optional-auth chat conversation/message reads and sender impersonation (`chat.controller.ts:246-269`, `341-388`, `441-465`), ride creation/booking/update/delete (`rides.controller.ts:37+`), item-delivery lifecycle operations (`items-delivery.controller.ts:25+`), and mass session logout (`session.controller.ts:207-228`). - File: `apps/api/src/controllers/` and `apps/api/src/auth/controllers/session.controller.ts` -> Action: Establish a route-level access-control matrix, apply JWT/admin guards and resource ownership checks, derive user IDs from the token, redact PII, and add end-to-end authorization tests before release.
* **[HIGH] Any JWT holder can request an arbitrary manager's hours report.** SRS §2.11.4 explicitly requires `AdminAuthGuard`, but `GET /api/tasks/hours-report/:managerId` uses only `JwtAuthGuard` and trusts the path manager ID (`tasks.controller.ts:568-573`). - File: `apps/api/src/tasks/tasks.controller.ts` -> Action: Apply `AdminAuthGuard`, derive or authorize the requested manager scope against the JWT actor, and add non-admin/cross-manager denial tests. The broader visibility policy for `GET /api/tasks` remains underspecified and should be resolved separately.
* **[HIGH] Known vulnerable dependencies remain in the lockfile.** A fresh `npm audit --workspaces --audit-level=moderate --json` on 2026-07-14 reports **85 vulnerabilities** (2 critical, 69 high, 12 moderate, 2 low). Critical transitive findings include `handlebars` code injection and `shell-quote` command injection; direct high findings include `@nestjs/platform-express` through `multer`, `axios@1.15.2`, and `protobufjs@7.5.5`. - File: `package-lock.json`, root and workspace `package.json` files -> Action: Upgrade direct dependencies and overrides, regenerate the lockfile, rerun tests/audit, and determine whether vulnerable build-only chains process untrusted input.

## 🐞 Bugs & Logic Issues

* **Editing a post can persist a device-local image URI and delete secondary images.** The picker stores `file://`/`content://` URIs (`EditPostModal.tsx:51-75`) and sends them without upload (`EditPostModal.tsx:97-121`, `postsService.ts:342-350`). The API then replaces the entire `images` array with one string (`posts.controller.ts:2349-2356`). Other devices cannot load the local URI, and a multi-image post silently loses every image after the first. - Recommendation: Upload newly selected local assets before the update and send the complete `images[]` contract; preserve unchanged secondary images and test local, remote, removal, and multi-image cases.
* **The default admin-task request disables server root-only filtering, then removes subtasks after pagination.** The client always sends default non-done statuses (`useAdminTasksScreen.tsx:329-376`), so the server considers the request filtered and skips `parent_task_id IS NULL` (`tasks-list-query.service.ts:136-155`). The client subsequently filters roots (`useAdminTasksScreen.tsx:179-186`), producing sparse or empty pages and hiding root tasks behind subtask-heavy offsets. - Recommendation: Add an explicit `root_only` API parameter and apply it independently of other filters; cover the default client request with an integration test.
* **Admin infinite scroll can skip pages.** Load-more does not set `loading`, and `loadMore` has no in-flight ref (`useAdminTasksScreen.tsx:220-225`, `352-426`). Repeated `onEndReached` calls can advance page 0 → 2 while the sequence guard discards page 1. - Recommendation: Add a synchronous in-flight guard/loading-more state, advance the cursor only after success, and deduplicate appended task IDs.
* **Concurrent API requests can hang forever after refresh failure.** A second 401 subscribes to token refresh, but the failure path clears the callback array without resolving or rejecting waiting promises (`authFetchInterceptor.ts:46-89`). - Recommendation: Store resolve/reject subscribers, reject all waiters on refresh failure, unify session clearing with the primary user store, and add concurrent-success/failure tests.

## 🏗️ Architecture & Clean Code

* **The target Infrastructure → Application → Domain dependency direction and layer boundaries are absent.** No tracked source files exist under a `domain` or `application` directory. Business rules, HTTP mapping, PostgreSQL, Redis, and schema mutation are combined in NestJS controllers/services; mobile state, REST/Firestore access, caching, and persistence are combined in `utils` and stores.
* **Infrastructure executes inside request controllers.** `posts.controller.ts` is 2,741 lines and performs DDL, SQL, caching, feed mapping, social actions, and moderation. `rides.controller.ts`, `donations.controller.ts`, `stats.controller.ts`, and `community-group-challenges.controller.ts` follow the same pattern. This prevents isolated authorization tests and makes fail-open routes easy to introduce.
* **Mobile application behavior is coupled to infrastructure.** `apps/mobile/utils/databaseService.ts` (1,225 lines) combines REST, Firestore, AsyncStorage, caching, and business behavior; `apiService.ts` and `userStore.ts` also carry cross-domain policy. Incremental extraction should start with permission rules, post-image update orchestration, task pagination, and token-refresh coordination behind ports.
* **Privacy enforcement required by SRS §2.5.7 remains absent.** The existing SSOT gap records that `posts.anonymity_level`, server-side visibility filtering, operator matching, and mobile selection UI are not implemented. Until that work exists, sensitive Level 1–3 post behavior described by the SRS must not be represented as available or secure.
