## 🚨 Critical Vulnerabilities

* **[CRITICAL] Live-looking infrastructure credentials and user backup data remain committed to Git.** Tracked `railway_vars.txt` still embeds credentialed `DATABASE_URL`, Redis URL, Google API key, and JWT secret material; `railway.toml.dev` embeds another JWT secret; `main.ts` hardcodes recognizable DB/Redis password fragments for environment fingerprinting; 49 tracked backup JSON files under `data-backups/20251224-162421/` include emails, phones, and Argon2 password hashes. - File: `apps/api/railway_vars.txt`, `apps/api/railway.toml.dev:34`, `apps/api/src/main.ts:149-214`, `apps/api/data-backups/20251224-162421/` -> Action: Rotate every exposed credential and session, purge secrets/PII from Git history, replace secret-fragment env detection with non-secret deployment identifiers, and enable CI secret scanning.
* **[CRITICAL] `POST /api/users/resolve-id` still mints victim JWTs from identifier knowledge alone.** The unguarded route accepts `email` / `firebase_uid` / `google_id`, resolves/links profiles, and returns access/refresh tokens carrying the matched user's roles — without verifying a provider token or password. Knowing an admin email is enough to obtain admin tokens. - File: `apps/api/src/controllers/users.controller.ts:183-188`, `apps/api/src/services/user-auth.service.ts:270-342,645-660` -> Action: Require verified Firebase/Google identity proof (or an already authenticated session); never mint KC JWTs from an email/UID string alone; add rate limits, audit logs, and negative tests. Conflicts with NFR §3.2; functional §2.1.6 currently documents the unsafe contract (gap logged).
* **[CRITICAL] Profile and hierarchy authorization still trust attacker-controlled identifiers.** `PUT /api/users/:id` has no self-or-admin ownership check and writes privileged fields including `roles` and `firebase_uid`; promote/demote/volunteer routes authorize body `requestingAdminId` instead of `req.user`; `set-manager` skips the admin gate when `requestingUserId` is omitted. Any ordinary JWT can escalate roles or rewrite hierarchy. - File: `apps/api/src/controllers/users.controller.ts:45-89,126-132`, `apps/api/src/services/user-profile.service.ts:254-361`, `apps/api/src/services/user-hierarchy.service.ts:492-517,945-1050` -> Action: Derive the actor only from `req.user`, enforce `AdminAuthGuard` for privileged ops, restrict profile DTOs to safe self-fields, and remove client-supplied actor IDs.
* **[CRITICAL] Private data and state-changing APIs remain reachable without effective authentication.** `OptionalAuthGuard` on chat allows anonymous conversation/message access and `sender_id` spoofing; rides, dedicated items, generic items, item-delivery, CRM, and community-members mutation routes lack guards; session endpoints permit enumeration/forced logout by `userId`; the production-registered rate-limit controller allows anonymous limiter clears. - File: `apps/api/src/controllers/chat.controller.ts:45-47`, `apps/api/src/controllers/rides.controller.ts:37-48`, `apps/api/src/items/dedicated-items.controller.ts`, `apps/api/src/items/items.controller.ts`, `apps/api/src/controllers/items-delivery.controller.ts`, `apps/api/src/controllers/crm.controller.ts`, `apps/api/src/controllers/community-members.controller.ts`, `apps/api/src/auth/controllers/session.controller.ts`, `apps/api/src/controllers/rate-limit.controller.ts` -> Action: Enforce a route permission matrix (JWT/admin), bind ownership to the session actor, verify chat membership, and exclude diagnostic controllers from production.
* **[CRITICAL] Guarded post mutations still accept a spoofed body actor.** Like (and related comment) handlers use `body.user_id` rather than `req.user.userId`, so any valid JWT can attribute likes/notifications to another user. - File: `apps/api/src/controllers/posts.controller.ts:1343-1405` -> Action: Remove client-supplied actor IDs from guarded DTOs; use the authenticated subject exclusively.
* **[CRITICAL] Request- and startup-path `DROP TABLE ... CASCADE` can destroy production data.** Public `GET /api/posts` runs `ensurePostsTable()` / `ensureLikesCommentsTable()` which may drop `posts`, `post_likes`, `post_comments`, and `comment_likes`; task schema helpers can drop `posts`; startup compatibility drops legacy `donations`/`rides` (enabled when `SKIP_FULL_SCHEMA=1`, which is set in committed Railway vars). - File: `apps/api/src/controllers/posts.controller.ts:67-79,305-374`, `apps/api/src/tasks/tasks-schema.service.ts:18-42`, `apps/api/src/database/database.init.ts:52-86,563-670` -> Action: Remove destructive DDL from request/startup paths; use reviewed versioned migrations with backups and fail closed on schema mismatch.

## 🐞 Bugs & Logic Issues

* **Database initialization failure is treated as non-fatal.** Outer catch logs “Non-fatal, continuing startup” and does not rethrow, so health can pass against a partial/broken schema. - File: `apps/api/src/database/database.init.ts:80-86` -> Recommendation: Fail startup/readiness in production when required migrations fail; gate non-fatal behavior to an explicit development-only flag.
* **Concurrent requests can hang forever after token refresh failure.** Waiting 401 callers subscribe success-only callbacks; the failure path clears `refreshSubscribers` without resolving those promises. - File: `apps/mobile/auth/interceptors/authFetchInterceptor.ts:9-19,46-89` -> Recommendation: Store resolve/reject waiters and settle all waiters on both success and failure; add concurrent refresh tests.
* **Closed-profile task deduplication uses inconsistent type discriminators.** Post-derived closed tasks are typed `task`, while tasks loaded from the tasks API are typed `task_post`; dedupe relies on nested `taskData.id` from `p.task`, so missing nested task payloads still produce duplicates. - File: `apps/mobile/bottomBarScreens/profile/ClosedRoute.tsx:100-104,320-351` -> Recommendation: Normalize to one discriminator, prefer `taskId`/`taskData.id` fallbacks, and add a regression test for overlap.
* **[NEW] Task “done” side effects can insert duplicate completion posts.** Status PATCH still runs completion side effects when `body.status === "done"` even if the task was already done / the assignment post already converted, so repeated or concurrent done transitions create extra completion posts. - File: `apps/api/src/tasks/tasks.controller.ts:478-521`, `apps/api/src/tasks/tasks-side-effects.service.ts:447-477` -> Recommendation: Gate side effects on an actual status transition (`oldStatus !== "done"`) inside a transactional lock; add an idempotency test.
* **[NEW] Ride booking has an oversell race.** `POST /api/rides/:id/book` checks `remaining_seats` then inserts without `SELECT … FOR UPDATE`, serializable isolation, or an atomic conditional update, so concurrent bookings can both succeed past capacity. - File: `apps/api/src/controllers/rides.controller.ts:374-468` -> Recommendation: Lock the ride row (or use an atomic seats decrement with a CHECK) inside the booking transaction; add a concurrency test.
* **[NEW] Task listing/detail leaks admin task data to any authenticated user.** `GET /api/tasks` and related detail/subtree routes use `JwtAuthGuard` without admin or assignee/hierarchy scoping, so any valid JWT can enumerate tasks and creator/assignee details. - File: `apps/api/src/tasks/tasks.controller.ts:74-146,191-249` -> Recommendation: Require `AdminAuthGuard` for admin views or enforce row-level visibility from `req.user`; include actor identity in cache keys.
* **Hierarchy notifications write to a table the client does not poll.** Transfer logic inserts into `notifications`, while the notification API reads `user_notifications`. - File: `apps/api/src/services/user-hierarchy.service.ts:834-855`, `apps/api/src/controllers/notifications.controller.ts` -> Recommendation: Persist through one application port and migrate existing rows.
* **Legacy email login can succeed without verifying a password.** Verification runs only when both request password and stored hash exist; otherwise the endpoint still returns the matched profile/roles (no JWT on this path today). - File: `apps/api/src/services/user-auth.service.ts:205-263` -> Recommendation: Always require and verify credentials; return a generic auth error; throttle; add missing/wrong-password tests. SRS: §2.1.2.
* **Unauthenticated ride/item creation can spoof feed authors.** Client-supplied `driver_id` / `owner_id` become linked `posts.author_id`, attributing feed content to victims. - File: `apps/api/src/controllers/rides.controller.ts`, `apps/api/src/items/dedicated-items.service.ts`, `apps/api/src/controllers/items-delivery.controller.ts` -> Recommendation: Require auth and bind author/owner fields to `req.user.userId`.

## 🏗️ Architecture & Clean Code

* **Security-sensitive god objects far exceed the ~200 LOC target.** Approximate sizes at HEAD: `posts.controller.ts` 2,741; `stats.controller.ts` 1,709; `user-hierarchy.service.ts` 1,675; `database.init.ts` 1,374; mobile `databaseService.ts` 1,225. Extract identity/permission policies and transactional use cases behind ports before further feature work in these files.

* **SRS contains unsafe auth/chat contracts that conflict with NFR security.** Functional §2.1.6 documents identifier-only JWT minting; §2.7 / §3.2 document `OptionalAuthGuard` guest access while §3.2/§3.5 also require authorization and data minimization. Prefer NFR security and amend the functional shards (gap logged in `docs/SSOT/SRS/10-gaps-and-assumptions.md`).
* **Required post anonymity enforcement is still absent.** No `anonymity_level` column/filtering/redaction exists, so Level 1–3 author privacy from SRS §3.2/§3.5 cannot be enforced server-side.
