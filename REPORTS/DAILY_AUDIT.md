## 🚨 Critical Vulnerabilities

* **[CRITICAL] Live-looking infrastructure credentials and user backup data are committed to Git.** `railway_vars.txt` contains a credentialed database URL, Redis URL, Google API key, and JWT secret; `railway.toml.dev` contains another JWT secret; `main.ts` embeds recognizable database and Redis credential fragments; 49 tracked backup files include user emails, phone numbers, and password hashes. - File: `apps/api/railway_vars.txt:8-38,85-90`, `apps/api/railway.toml.dev:34`, `apps/api/src/main.ts:149-213`, `apps/api/data-backups/20251224-162421/` -> Action: Rotate every exposed credential and active token session, purge secrets and PII from Git history, replace credential-fragment environment detection with non-secret deployment identifiers, and enable CI secret scanning.
* **[CRITICAL] `POST /api/users/resolve-id` mints victim JWTs from identifier knowledge alone.** The unguarded route accepts email, Firebase UID, or Google ID, queries profiles with OR matching, links supplied identifiers, and creates an access/refresh token pair carrying the matched user's roles. A caller who knows an admin email can obtain admin tokens without proving identity. - File: `apps/api/src/controllers/users.controller.ts:183-188`, `apps/api/src/services/user-auth.service.ts:270-342,360-381,645-672` -> Action: Require a verified provider token, password, or authenticated session; bind identifiers to the verified subject; never issue tokens from an email lookup; add rate limiting, audit logging, and negative tests. SRS: §2.1.6 and §3.2.
* **[CRITICAL] Profile and hierarchy authorization trusts attacker-controlled identifiers.** `PUT /api/users/:id` does not enforce self-or-admin ownership and accepts privileged fields including `roles` and `firebase_uid`; promotion routes authorize the body `requestingAdminId`; `set-manager` skips the admin check when `requestingUserId` is omitted. Any ordinary JWT can therefore escalate roles or mutate another user's hierarchy. - File: `apps/api/src/controllers/users.controller.ts:55-89,126-132`, `apps/api/src/services/user-profile.service.ts:285-361`, `apps/api/src/services/user-hierarchy.service.ts:492-517,600-615,945-980` -> Action: Derive the actor only from `req.user`, use `AdminAuthGuard` for privileged operations, enforce self-or-admin profile ownership, and remove privileged fields and actor IDs from public DTOs. SRS: §2.2.1 and §2.2.3.
* **[CRITICAL] Private data and state-changing APIs remain reachable without effective authentication.** `OptionalAuthGuard` permits anonymous chat conversation/message reads and sender impersonation; ride and item-delivery mutation controllers have no guards; CRM CRUD exposes contact data; session endpoints permit enumeration and forced logout; the production-registered rate-limit controller lets anonymous callers clear limiter keys. - File: `apps/api/src/controllers/chat.controller.ts:45-46,246-269,341-465`, `apps/api/src/controllers/rides.controller.ts:37-48`, `apps/api/src/controllers/items-delivery.controller.ts:25-70`, `apps/api/src/controllers/crm.controller.ts:38-70`, `apps/api/src/auth/controllers/session.controller.ts:163-228`, `apps/api/src/controllers/rate-limit.controller.ts:152-181` -> Action: Define and enforce a route permission matrix, require JWT/admin guards, bind all ownership fields to the session actor, verify chat membership, and exclude diagnostic controllers from production.
* **[CRITICAL] Guarded post mutations still accept a spoofed body actor.** Like and related comment actions use `body.user_id` instead of the authenticated subject, allowing any valid JWT to create activity and notifications attributed to another user. - File: `apps/api/src/controllers/posts.controller.ts:1343-1405` and related comment handlers -> Action: Remove client-supplied actor IDs from guarded DTOs and use `req.user.userId` exclusively.

## 🐞 Bugs & Logic Issues

* **Ordinary requests and startup can delete production data.** Post schema checks execute `DROP TABLE ... CASCADE` when legacy columns are missing; startup compatibility code similarly drops legacy donations and rides, including dependent rows. - File: `apps/api/src/controllers/posts.controller.ts:67-79,305-374`, `apps/api/src/tasks/tasks-schema.service.ts:27-42`, `apps/api/src/database/database.init.ts:558-568,660-670` -> Recommendation: Remove DDL from request paths, replace destructive compatibility branches with reviewed versioned migrations, use backups and transactions, and fail closed on schema mismatch.
* **Database initialization failure is treated as non-fatal.** Any core schema or compatibility error is logged and swallowed, allowing health checks to pass while endpoints run against a partial schema. - File: `apps/api/src/database/database.init.ts:55-86` -> Recommendation: Fail startup or readiness when required migrations fail and run migrations once under an advisory lock.
* **Concurrent requests can hang forever after token refresh failure.** Waiting 401 requests register success-only callbacks; the failure path clears the subscriber list without resolving or rejecting those promises. - File: `apps/mobile/auth/interceptors/authFetchInterceptor.ts:9-19,46-89` -> Recommendation: Store resolve/reject waiters, settle all waiters on both success and failure, and add concurrent refresh tests.
* **Closed-profile task deduplication compares incompatible type values.** Existing task posts are emitted as `task_post`, but deduplication filters for `task`, so completed and archived tasks can be displayed twice. - File: `apps/mobile/bottomBarScreens/profile/ClosedRoute.tsx:320-351` -> Recommendation: Normalize the type discriminator and add a test covering a task present in both post and task responses.
* **Hierarchy notifications are written to a table the client does not read.** Task-transfer logic writes `notifications`, while the notification API polls `user_notifications`, so affected users silently miss updates. - File: `apps/api/src/services/user-hierarchy.service.ts:834-855`, `apps/api/src/controllers/notifications.controller.ts:135-182` -> Recommendation: Consolidate notification persistence behind one application port and migrate existing rows.
* **Legacy email login reports success without verifying a password.** Verification runs only when both a request password and stored hash exist; otherwise the endpoint returns the matched profile and roles, although this path currently does not issue JWTs. - File: `apps/api/src/services/user-auth.service.ts:205-263` -> Recommendation: Require and verify the credential, return a generic authentication error, apply throttling, and add missing/wrong-password tests. SRS: §2.1.2.

## 🏗️ Architecture & Clean Code

* **The documented Infrastructure → Application → Domain boundary is not implemented.** No source domain/application layers isolate core policy; controllers and mobile utilities directly combine authorization, SQL, transactions, cache invalidation, schema mutation, and presentation mapping.
* **Security-sensitive god objects exceed the documented complexity target by an order of magnitude.** `posts.controller.ts` is about 2,741 lines, `user-hierarchy.service.ts` about 1,675, `database.init.ts` about 1,374, and mobile `databaseService.ts` about 1,225. Incrementally extract identity/permission policies and transactional use cases behind ports before changing these areas.
* **Runtime DDL is owned by HTTP controllers.** `PostsController` and task services detect and mutate schema during user traffic, coupling infrastructure migration concerns to request handling and creating the destructive failure modes above.
* **The SRS contains an unsafe chat contract conflict.** Functional §2.7 documents `OptionalAuthGuard` and guest reads, while security/privacy §3.2 and §3.5 require authorization and server-side data minimization; the implementation exposes private conversation metadata, messages, and anonymous sender impersonation. Resolve the requirement in favor of authenticated participant-only access.
* **Required post anonymity enforcement is absent.** The API contains no `anonymity_level` handling, so Level 1–3 visibility and author redaction required by SRS §3.2/§3.5 cannot be enforced server-side.

## 🧹 Technical Debt & Maintenance

* **Known dependency advisories lack a maintained merge gate.** A fresh `npm audit --workspaces --audit-level=moderate` observed 57 vulnerable packages: 3 critical, 40 high, 12 moderate, and 2 low. Critical-rated transitive packages were `handlebars`, `shell-quote`, and `websocket-driver`; runtime reachability was not established. Upgrade direct parents/overrides, regenerate the lockfile, verify reachability, and restore a CI dependency policy with documented exceptions.
* **Security-critical behavior has almost no negative regression coverage.** Add focused tests for identity proof, role mass assignment, hierarchy actor binding, chat membership, ride/item ownership, session ownership, spoofed post actors, rate-limit diagnostics, destructive migration rejection, and concurrent refresh failure.
* **Tracked backups and generated diagnostics create ongoing leak and review risk.** Remove or relocate the 49 database backup files plus generated compiler, lint, and ad hoc verification output; add appropriate ignore rules and sanitize history where sensitive.
* **Schema evolution is unversioned and duplicated.** Canonical SQL, startup compatibility DDL, request-path DDL, and standalone migration scripts drift independently; dual notification tables are one visible result. Adopt a single ordered migration ledger with checksums, transactions, rollback/backup procedures, and deployment ownership.
