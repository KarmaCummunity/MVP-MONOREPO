### 10.2 Assumptions

| # | Assumption |
|---|------------|
| 1 | The system is in **MVP/active development** phase — many tables exist without corresponding API endpoints (events, organizations) as forward schema provisioning |
| 2 | **Challenges `user_id` is VARCHAR** (not UUID) — assumed to be a separate identity system or legacy format; the mobile app may use string-based user IDs for challenges |
| 3 | **Donations and rides controllers** contain inline SQL without separate service files — assumed intentional for MVP speed, planned for refactoring |
| 4 | **Firebase is transitioning out** — `USE_FIRESTORE=false` default, `USE_BACKEND=true`; migration planning tracked in `docs/SSOT/CODE_QUALITY/tech-debt-log.md`; current architecture supports both but prefers REST |
| 5 | **Expo Router is deprecated** — returns null; real navigation is React Navigation stack/tab navigators |
| 6 | **Redis is optional** — the app runs without Redis but loses caching, sessions, rate limiting |
| 7 | The admin email allowlist on mobile (`EXPO_PUBLIC_ADMIN_EMAILS`) is a **client-side convenience** — actual admin enforcement is server-side via JWT roles |
| 8 | **`notifications` table** (in migrations) and **`user_notifications`** (in schema) may represent **duplicate/overlapping** notification storage — assumed migration in progress |
| 9 | **Concurrent FKs added via DO blocks** rather than inline — assumed for migration compatibility with existing data |
| 10 | **`volunteer_manager`** is treated as a **first-class role string** in `user_profiles.roles`; promotion and permission matrices may lag until implemented in API and mobile |
| 11 | **`operator`** will be treated as a **first-class role string** in `user_profiles.roles` once implemented. It is NOT an admin role — operators have access only to the matching workspace (§2.14), not to admin endpoints (§2.11). Admins/super_admins have implicit operator access. |
| 12 | **Operator matching is manual (human-in-the-loop)** — no automated ML recommendation is planned for the initial release. Future work may add scoring/suggestions but the SRS treats manual matching as the baseline. |
| 13 | **Shiduchim Tov** is a product-facing name only — the internal module is `operator-matching` and the slug is `shiduchim-tov`. It has no dependency on the existing `matchmaking` category or its data. |

### 10.3 Technical Debt & Risks

| Risk | Severity | Details |
|------|----------|---------|
| **Custom JWT implementation** | Medium | Hand-rolled HMAC-SHA256 JWT instead of battle-tested library (`jsonwebtoken`, `jose`). Functional but increases maintenance burden and attack surface |
| **No global exception filter** | Medium | Unhandled exceptions may leak stack traces in development. Production disables error messages via `ValidationPipe` but no catch-all filter |
| **Inline SQL injection risk** | Low-Medium | Most SQL uses parameterized queries (`$1`, `$2`), but complex queries with `pg-format` and string interpolation require careful review |
| **Dual notification tables** | Low | `user_notifications` and `notifications` may cause confusion; migration to unify needed |
| **No database migration tool** | Medium | Schema changes managed via SQL files and DO blocks — no Prisma/TypeORM/Knex migrations with version tracking. Adding matching tables (§6.1.13) will require careful manual migration. |
| **Client-side admin check** | Low | `EXPO_PUBLIC_ADMIN_EMAILS` on mobile is a convenience; server enforces roles. Risk: UI shows admin features to non-admin if env misconfigured |
| **Console.log in Redis cache service** | Low | `redis-cache.service.ts` uses `console.warn` instead of NestJS Logger — violates project coding standards |
| **Polling-based notifications** | Medium | 5-second polling interval creates unnecessary server load at scale; WebSocket or server-sent events would be more efficient. Operator queue polling adds to this load. |
| **No API versioning** | Medium | All routes under `/api/` with no version prefix — breaking changes affect all clients simultaneously. Adding `/api/operator/*` endpoints is safe but future versioning is recommended. |
| **No rate limiting on all endpoints** | Low | `ThrottlerGuard` only on `AuthController` and `NotificationsController`. `ThrottlerModule` is not registered as `APP_GUARD`. Operator endpoints need their own rate-limit tier (§3.1). The `JwtAuthGuard` bucket is not per caller — see the High rows below. |
| **JWT rate-limit key is the shared JOSE header, and `/rate-limit/custom` can plant it** | High | NFR §3.1 says “100 requests per 60 seconds per token prefix.” `JwtAuthGuard` calls `checkRateLimit(token.substring(0, 16), "api_access", …)` before `verifyToken`. Every HS256 access token shares one prefix, so the Redis block key is global for that algorithm. `POST /rate-limit/custom` has no guard. Its body type is a TypeScript interface, so the global `ValidationPipe` does not whitelist it. `customKey` becomes the Redis rule type. One request with that prefix as `identifier`, `customKey` = `api_access`, `rule.requests` = `0`, and a positive `blockDurationMs` writes the same block key for an attacker-chosen TTL. Every `JwtAuthGuard` route then returns 401 until the key expires. One hundred forged Bearer requests through the guard produce the same 5-minute lockout. Absent from `dev` until the 2026-09-24 audit. Carried forward on 2026-09-28 because PRs `#169` through `#173` are still unmerged. |
| **`/session/login` shares one IP bucket, and `/rate-limit/stress-test` can fill it** | High | No `trust proxy` setting exists under `apps/api`. Nest `@Ip()` is Express `req.ip`, the immediate TCP peer. `POST /session/login` rate-limits that peer under rule `login` (5 requests / 15 minutes, then a 30-minute block) before `argon2.verify`. `POST /rate-limit/stress-test` is unauthenticated, defaults `identifier` to the same `@Ip()`, and loops `checkRateLimit` up to 50 times. One call with `{ "ruleType": "login", "requests": 6, "delayMs": 0 }` writes `blocked:login:<peer>`. Behind the committed Railway proxy, every client shares that peer, so password-verified session login fails closed for the whole process until the block expires. `POST /rate-limit/custom` can set the same key with an uncapped `blockDurationMs`. Carried forward on 2026-09-28 because PRs `#170` through `#173` are still unmerged. |
| **Email-only `resolve-id` plus omitted `requestingUserId` rewrites the org tree** | High | `POST /api/users/resolve-id` has no guard. An email match mints an access and refresh pair that copies `user_profiles.roles` (`user-auth.service.ts` 328–342, 645–660). `POST /api/users/:id/set-manager` is `JwtAuthGuard` only and never reads `req.user` (`users.controller.ts` 45–52). `setManagerEnsureRequesterAdminIfProvided` returns success when `requestingUserId` is omitted or not found (`user-hierarchy.service.ts` 492–516), then `setManager` updates `parent_manager_id` (600–628). `POST :id/hierarchy/manage` has no actor field and applies add/remove for any JWT (55–62, 871–914). A known email is enough to obtain that JWT and move non-root users in the hierarchy. The root-admin email is still blocked as a target. Logged 2026-09-25. Carried forward on 2026-09-28 because PRs `#171` through `#173` are still unmerged. Supplying a public admin id to promote-admin is a separate escalation; see the 2026-09-27 row. |
| **Comment edit and delete trust the client `user_id`** | High | SRS §2.5.3 requires `JwtAuthGuard` on `PUT /api/posts/:postId/comments/:commentId` and `DELETE /api/posts/:postId/comments/:commentId`. The handlers never read `req.user`. Update compares `post_comments.user_id` to `body.user_id` (`posts.controller.ts` 1985–2014). Delete compares it to query `user_id` (2058–2087). `GET /api/posts/:postId/comments` has no guard and returns `c.user_id` (1726–1743). Any access token, including one minted by unauthenticated `resolve-id`, can rewrite or remove another user's comment and adjust `posts.comments`. Logged 2026-09-26. Carried forward on 2026-09-28 because PRs `#172` and `#173` are still unmerged. The 2026-09-13 like/comment bullet covers create and like spoof only. |
| **Public admin id grants `admin` via promote-admin** | High | `POST /api/users/:id/promote-admin` is `JwtAuthGuard` only and never reads `req.user` (`users.controller.ts` 64–70). `promoteToAdmin` treats body `requestingAdminId` as the actor (`user-hierarchy.service.ts` 945–1049). `GET /api/users` and `GET /api/users/search` have no guard and return `id`, `email`, and `roles` (`user-profile.service.ts` 68–75, 503–516). `assertRequesterMayPullTargetUnderSelf` returns success when the named admin is not already above the target and the target is not an ancestor (93–149). Register does not set `parent_manager_id` (`user-auth.service.ts` 107–112), so a new profile is eligible. A second unauthenticated `POST /api/users/resolve-id` reloads `roles` into a new JWT (645–660), which then satisfies `AdminAuthGuard`. The root-admin email is still blocked as a target. `promote-volunteer` uses the same body actor (82–88, 1306–1407). `demote-admin` impersonates the named admin for that admin's subtree, and any public `super_admin` id skips the subordinate check (1120–1194). Logged 2026-09-27. Carried forward on 2026-09-28 because PR `#173` is still unmerged. |
| **Unauthenticated hierarchy tree returns salary and seniority** | High | SRS §2.2.3 lists `GET /api/users/hierarchy/tree` among endpoints that require `JwtAuthGuard`. The handler has no guard (`users.controller.ts` 96–98). `getFullHierarchyTree` selects `salary` and `seniority_start_date` for every node under the root admin (`user-hierarchy.service.ts` 1529–1566) and copies both onto the JSON tree (411–425). The same request calls `ensureSalarySeniorityColumns` (1506), which can `ALTER TABLE user_profiles` to add `salary`, `seniority_start_date`, and `parent_manager_id` (436–483) with no authentication. `GET /api/users/:id/hierarchy` is also unguarded (106–108) and returns subordinate name and email; that query does not select salary. NFR §3.5 requires the server to omit fields the caller is not allowed to see. Logged 2026-09-28. |
| **Hebrew in codebase** | Low | README, docs, some Dockerfile comments, and iOS `infoPlist` strings contain Hebrew — violates English-only code comments rule but acceptable in user-facing strings and documentation |
| **No Prisma/ORM** | Info | Deferred; see `docs/SSOT/CODE_QUALITY/tech-debt-log.md`. Current raw SQL works but makes schema changes harder to track |
| **Anonymity enforcement complexity** | Medium | Implementing server-side anonymity filtering in `PostsService.getPosts()` requires per-request role checking and follower-set joins, which may degrade feed query performance without proper indexing (add index on `posts.anonymity_level`). |
| **Operator PII access audit** | Medium | Without proper audit logging from day one, it will be difficult to retrospectively demonstrate compliance with privacy requirements. Audit tables (§6.1.13) should be created alongside the matching module. |
